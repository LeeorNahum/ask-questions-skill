# Eval Harness

Runs clean-room agent sessions on the cases in `../evals.json`, each in a copy of a fixture project from `../fixtures`, and grades whether the session asked what it should and nothing else. Maintainer-only.

`run.py` follows the clean-room shape of the context-memory harness (an isolated config folder holding only the CLI's credentials, a run folder outside the home folder and every Git repository, the skill copied where each CLI discovers project skills), with these differences:

- A case has `turns`. The first turn starts a session, and each later turn resumes that same session (`claude -p --resume <id>`, `codex exec resume <id>`), so the conversation carries over. Each turn keeps its own record and the commit before it, so an assertion can grade one turn.
- The environment passed to the CLI is an allowlist, so nothing the maintainer exported reaches a session.
- Runs are headless and nobody answers. In `claude -p` the question tool is not offered at all, so the skill's fallback applies and a session asks in its messages. `codex exec` has not been probed yet. Checks that forbid asking read the final message, since an agent thinking aloud in commentary is not asking the user, and a semantic assertion has the critics judge every message of the turn by meaning. `grade.py` keeps the check that no question-tool call was attempted as a setup guard: a host that starts offering the tool in headless runs shows up there first.
- Whether a message asks about a settled topic is a question of meaning, so those clauses are semantic and graded by critics. Checks count only what code can count.

`grade.py` holds one function per check id and writes blind packages for the semantic assertions. Use the `batch.py` shipped here, which runs `run.py` with `-B`. Copy `CRITIC.md` from the [web-repository-opinions harness](https://github.com/LeeorNahum/web-repository-opinions-skill/tree/main/evals/harness) and change the inputs to `turns.json`, `semantic.json`, and per letter `turn-<n>-answer.txt`, `turn-<n>-messages.txt` (every message of the turn), `turn-<n>-diff.txt`, and `project/`, graded turn by turn. Take `compare.py` from web-repository-opinions' harness rather than context-memory's, because it accepts a pass only with evidence, and point its expected-job list at this suite's cases. It compares the old and new arms. Read the `none` arm's grades directly, since that comparison expects every session to have read the skill.

This skill is meant to load when a turn waits on the user. A session with nothing to ask rightly never loads it, and in a smoke run neither an invitation to ask nor naming the skill changed that, so its pass says nothing about the skill's instructions, which are what over-questioning and repeated settled questions come from. Each pressure case therefore opens by asking the session to load the skill, which a smoke run confirmed makes it load in `claude -p`. The `none` arm gets the same turns without that sentence. Whether the description triggers on its own is a separate question for a trigger evaluation, not these cases. `grade.py` reports a skill-arm session that still never loaded it as not measured, whether its checks passed or failed. Run a `none` arm with no skill installed beside the old and new arms, so a round shows the skill's effect against no skill as well as one version against another.

The restraint cases, `decision-only-the-user-can-make` and `one-decision-at-a-time`, guard the opposite failure: a change that stops over-questioning must not stop the agent from handing back a decision that is the owner's, or make it ask several at once. They leave out the load sentence, because a turn that waits on the user is what the description triggers on, so a session that never loads the skill there, which `grade.py` reports as not measured, is itself a finding.

What these cases cannot show is the interactive path, where a person answers through the question tool. That needs a simulated responding user and is left out of this suite.
